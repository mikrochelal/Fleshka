# THE LAST SIGNAL — Game Design Document

Version 0.1 · living document · design intent, not implementation status
(for status see `PROGRESS.md`).

## 1. Overview

| Item      | Value                                                         |
| --------- | ------------------------------------------------------------- |
| Genre     | Psychological / atmospheric co-op horror, mystery, exploration |
| Players   | 1–4 per session                                               |
| Playtime  | 15–25 minutes                                                 |
| Platforms | Roblox PC + mobile                                            |
| Pillars   | Dread over jumpscares · fair monster · readable puzzles · co-op by radio |

## 2. Story

1998. STATION-09, an underground facility, studies an anomalous electromagnetic signal.
Staff report radios carrying voices of colleagues who are elsewhere, camera silhouettes in
empty corridors, messages from sealed rooms, and recordings of their own voices saying
things they never said. On 17 October 1998 contact is lost. The last transmission:
**"IT KNOWS WE ARE LISTENING."**

Years later a new signal appears. The players are the team sent to restore communications,
investigate, and retrieve the archive. The station is not empty.

The truth, never stated outright: the signal is not a message, it is the entity's means of
copying. Everything that listens to it is learned by it. Restoring the transmitter is what
it wanted. Origin stays unexplained.

## 3. Session flow

```text
Main Menu → Lobby (party, ready) → Loading → Story intro (text) → Cinematic intro
→ Gameplay: Entrance → Corridors → Laboratory → Communication Center
→ Final sequence (escape to elevator) → Ending cinematic → Credits → Main Menu
```

Server phases (`Shared/GameState.luau`): `Lobby → Loading → Intro → Playing → Finale →
Ending → Lobby`.

### Lobby and sessions (technical decision)

One Roblox place runs in two modes:

- **Lobby server** (public): main menu, party creation/joining, ready checks. When a party
  starts, the server reserves a private server of the same place with
  `TeleportService:ReserveServer` and teleports the party there.
- **Session server** (reserved): detected via `game.PrivateServerId`; runs the story for
  that party only.
- **Studio / solo fallback**: teleporting does not work inside Studio, so in Studio the
  session starts in the same server. This keeps the whole game testable with Play.

Progress is session-based: nothing persists between sessions except client settings.

## 4. World — STATION-09

| Area                      | Purpose                         | Landmarks                                   | Gameplay                              |
| ------------------------- | ------------------------------- | ------------------------------------------- | ------------------------------------- |
| A. Entrance / Security    | Onboarding, first clues         | Freight elevator, checkpoint booth, lockers | Flashlight tutorial, first documents, breaker panel 1 |
| B. Research Corridors     | Tension, navigation             | Long main corridor, camera monitors, numbered doors | Power puzzle, first sightings, code clues |
| C. Experimental Laboratory | Lore core                       | Signal chamber, tape archive, evacuation mess | Frequency puzzle, recordings, code clues |
| D. Communication Center   | Climax                          | Radio mast base, central computer, keypad door | Security code, final transmission, escape |

Layout is a loop with one-way shortcuts that unlock as power returns, so the escape route
runs back through familiar, now-changed spaces. Each area has one dominant colour accent
(red emergency, cyan monitors, cold white lab light) for orientation.

## 5. Player systems

- **Movement:** walk 10 studs/s, sprint 17 studs/s. Sprint drains stamina (about 6 s full
  drain, 9 s regen, short regen delay; exhausted state forces walking until 25%).
- **Flashlight:** toggle; battery drains while on (about 6 minutes), battery pickups in the
  world; flickers below 15%. Light is visible to other players and to THE COPY.
- **Interaction:** proximity-based prompts (E / tap). Client requests, server validates
  distance, line of sight, phase and cooldown.
- **Documents:** collected to a shared team journal; some contain puzzle clues.
- **Radio:** scripted transmissions with subtitles; text quick-messages between teammates;
  the entity imitates transmissions.
- **Objectives:** server-driven list, one active objective shown in the HUD.
- **Failure:** a caught player is "taken" and returns at the last checkpoint after a delay.
  If every player is taken at once, the team restarts from the checkpoint. No permadeath.

All numbers are starting values and live in `ReplicatedStorage/Config`.

## 6. Puzzles

Solutions are generated by the server per session, so they cannot be memorised or read from
the client.

### 6.1 Power Restoration (Areas A–B)

Three breaker panels, each with four switches, plus a main lever. Maintenance memos found
nearby describe which circuits must be live ("Circuit 2 feeds the pumps — never with 4").
Players set breakers (state synchronised to everyone), then throw the main lever. Wrong
configuration: breakers trip, lights surge, noise draws THE COPY. Correct: power returns,
doors and shortcuts unlock.

### 6.2 Frequency Calibration (Area C)

A receiver with coarse and fine dials (87.5–108.0 MHz). The target is assembled from three
clue fragments in the lab. Feedback: static thins and a carrier tone sharpens as the needle
approaches; a signal-strength meter rises. The frequency must be held for three seconds to
lock. The server owns the dial value and validates the lock.

### 6.3 Security Code (Areas B–D)

A four-digit code. Each digit is written on a collectible clue with a colour tag; the order
of colours is shown on a faded sign by the keypad. Wrong entry: error tone and red flash;
three wrong entries lock the keypad for 20 seconds and alert THE COPY. Correct: the
Communication Center opens.

## 7. THE COPY

Tall humanoid, never fully lit, never explained.

| State         | Behaviour                                                                 | Leaves when                           |
| ------------- | ------------------------------------------------------------------------- | ------------------------------------- |
| Dormant       | Not present in the world                                                  | Tension budget or scripted trigger    |
| Observing     | Stands at a distant vantage point, watches, does not approach             | Seen for too long / approached → Disappearing; noise → Investigating |
| Investigating | Walks to the last noise (sprint, failed puzzle, flashlight seen)          | Finds nothing → Searching; sees player → Pursuing |
| Searching     | Checks nearby points for a limited time                                   | Timeout → Disappearing; sees player → Pursuing |
| Pursuing      | Chases the seen player, slightly faster than walking, slower than sprint | Loses sight for several seconds → Searching |
| Disappearing  | Fades out when unobserved or at distance                                  | Always → Dormant                      |

Fairness rules (hard constraints for the implementation):

- Never spawns within line of sight or closer than a minimum distance to any player.
- Every pursuit is preceded by an audible warning and a reaction window.
- A catch requires sustained proximity, never an instant touch.
- Cooldown after every pursuit; a tension budget limits total pressure per session.
- Behaviour is driven by player actions (noise, light, puzzle errors), not by dice.

Structure: one state machine module, one module per state, server-side pathfinding with
`PathfindingService`, senses (sight cone + noise events) as a separate module.

## 8. Scripted horror events

| # | Event                                   | Trigger                                 |
| - | --------------------------------------- | --------------------------------------- |
| 1 | Distant silhouette at corridor end      | First entry to the main corridor        |
| 2 | Radio plays a "recording" of a player   | After a document pickup in Area B       |
| 3 | Security monitor shows movement         | Looking at the monitor wall             |
| 4 | Facility lighting shuts down            | Shortly after power is restored         |
| 5 | A door opens by itself                  | Walking past a tagged door              |
| 6 | A message appears (terminal/wall)       | Returning to a previously visited room  |
| 7 | THE COPY appears briefly and vanishes   | Frequency lock                          |

Event 2 does not record real voice audio (not possible or permitted on Roblox). It replays
the player's own earlier radio quick-messages and name as distorted subtitles with static.

Each event runs once per session, is triggered by the server, and has a cooldown against
other events so they never stack.

## 9. Final sequence

Final transmission in the Communication Center → alarm, pursuit, escape to the elevator →
doors close, relief → a radio activates: **"Thank you for bringing it outside."** → fade to
black → short surface cinematic (a second signal answering) → credits → return to menu.

## 10. Visual, audio and UI direction

- Palette: dark grey, black, emergency red, muted cyan, cold white.
- Lighting: Future technology where the device allows, high contrast, subtle fog
  (`Atmosphere`), dust particles, restrained colour correction, film-grain/interference
  overlay for radio moments. Graphics setting scales effects for mobile.
- Audio: constant low room tone, positional sources, silence used deliberately.
- UI: built entirely in code (so it lives in Git), scale-based layouts, touch-size targets,
  safe-area aware. Screens: main menu (Play / Settings / Credits), lobby (player list,
  create/join party, ready, start), loading, HUD (stamina, battery, objective, prompt,
  subtitles), settings (master/music/SFX volume, camera sensitivity, subtitles, graphics),
  credits.

## 11. Technical architecture

```text
ReplicatedStorage
  Shared/    Loader, Logger, GameState, Net (remote definitions), types, utilities
  Config/    GameConfig + one config module per system
ServerScriptService/TheLastSignal
  Bootstrap  (only Script)
  Services/  SessionService, PlayerService, NetService, PartyService, ObjectiveService…
  Systems/   Interaction, Stamina, Flashlight, Puzzles/*, CopyAI/*, HorrorEvents/*…
StarterPlayerScripts/TheLastSignal
  ClientBootstrap (only LocalScript)
  Controllers/  UI screens, HUD, input, camera, audio, effects
```

- **Lifecycle:** bootstraps call `Loader.loadFolder`; modules expose `Init` then `Start`.
- **Networking:** remotes are declared in one shared module and created by the server.
  Every handler validates types, phase, player state and distance, and is rate limited.
  Clients send intent ("I want to flip breaker 3"), the server decides and replicates state.
- **State replication:** server-owned state is sent through remotes and instance attributes.
- **World contract:** the map is built in Studio and is not in Git. Code binds to it through
  CollectionService tags and attributes, never through fixed paths. Planned tags:

| Tag                | Put on                    | Attributes                         |
| ------------------ | ------------------------- | ---------------------------------- |
| `TLS_Interactable` | Part, Model or Attachment | `Kind`, `Id` (required strings); `ActionText`, `ObjectText` (optional) |
| `TLS_Document`     | Document pickup           | `DocumentId`                       |
| `TLS_Door`         | Door model                | `DoorId`, `RequiresPower`          |
| `TLS_BreakerPanel` | Power puzzle panel        | `PanelId`                          |
| `TLS_Light`        | Facility light            | `Circuit`                          |
| `TLS_Zone`         | Invisible area volume     | `Area`, `ZoneId`                   |
| `TLS_CopyVantage`  | Observation point         | `Area`                             |
| `TLS_Spawn`        | Spawn/checkpoint          | `Checkpoint`                       |

  The list is finalised when each system is implemented; a validator will report missing or
  misconfigured tags in the Output window at startup.

- **Map bootstrap:** because the map cannot be authored from this repository, Phase 6 ships
  an idempotent graybox generator that is run once from Studio. It creates a tagged
  blockout under a single `Workspace.Station09` model and refuses to run if that model
  already exists, so it can never overwrite hand-built work.

## 12. Assets
